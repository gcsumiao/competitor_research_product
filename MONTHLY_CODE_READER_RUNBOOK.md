# Monthly Code Reader Competitor Analysis — Operator Runbook

**Scope:** the full monthly cycle for the *code reader / scanner* category: raw data → two formatted Excel reports → dashboard update (local Docker Postgres) → production sync & Vercel deploy → QA.
**Repos involved (both live under this git root `/Users/sumiaoc/competitor_research_product`):**
- `Amazon_Monthly_Competitor_Report copy/` — the Python report pipeline ("report repo" below)
- `product_dashboard/` — the Next.js dashboard app
- Git remote: `origin = github.com/gcsumiao/competitor_research_product.git`, production branch: **`main`**

> Non-code categories (DMM, Backpack, Borescope, Jump Starters, Mechanic Stool, Smoke Machine, Thermal Imager, oil, stethoscope, …) have a **separate** flow (`reports:generate:non-code` → `sync:non-code-files` → `db:ingest:non-code`) and are NOT covered here. Do not mix the two.

## 2. Run the pipeline (produces the two formatted reports first, then everything else)

### One command (recommended)

From the git root:

```bash
pnpm db:up                                   # make sure local Postgres is up
pnpm prelaunch:code-reader -- --month YYYYMM
```

(Equivalent, from the report repo: `.venv/bin/python script/run_prelaunch_dashboard_pipeline.py --month YYYYMM`.)

Pipeline stages, in order:

1. **Preprocess** (`script/preprocess_month.py`) → builds `amazon_obd2/amazon_obd2_YYYYMM.xlsx`, checking every last-month ASIN is present and typed.
2. **Innova rules audit** (`script/audit_innova_monthly_rules.py`) → `script/runs/YYYYMM/innova_monthly_rules_audit.{csv,xlsx}`.
3. **Raw workbooks** (`script/full_report_month.py`) → into `script output reports/`: `Amazon Competitor Report.xlsx`, `summary.xlsx`, `dashboard_snapshot_rows.json`. Includes **generic brand recovery** (months ≥ 202608, see §2b).
4. **Dashboard ingest** → runs `product_dashboard/scripts/db-ingest-code-reader.mts` (Node/tsx, env from `product_dashboard/.env.local`) which writes the snapshot tables in Postgres and triggers cache revalidation.
5. **Formatted deliverables** (`script/automate_final_outputs.py`) → into `YY-MM-reports/` (see §3). Uses the previous month's finals as templates; fails instead of overwriting existing outputs unless `--overwrite-final`.

### 2b. Generic brand recovery (rule active from 202608, no backfill)

Helium10 marks uncaptured brands as `Generic`. From report month **202608** onward, `full_report_month.py` applies a recovery rule to rows with `Brand = generic` (analyst directive 2026-09-02):

- **Reassign:** if the Title *begins* with a known brand (window brands + `GENERIC_RECOVERY_EXTRA_BRANDS`, currently `nexiq`, `temeda`), the row moves to that brand. Mid-title mentions ("… for BMW", "Case for Innova") never match. Stopwords ("Universal", "Smart", …) never match.
- **Remove:** if the Title begins with **INNOVA or BLCKTEC**, the row is deleted from the month entirely (their numbers come from actuals; a raw generic row would double-represent them).
- **Audit:** every decision is written to `script/runs/YYYYMM/generic_brand_recovery.csv`, and one summary line prints per gated month (`reassigned= / removed= / mismatches= / unfrozen_candidates= / revenue_moved=`).
- **Freeze-and-replay:** the FIRST run of a month derives decisions and freezes them in that CSV; every later run (including future months re-loading this month as history) **replays the frozen CSV verbatim** — published numbers can never drift when the rolling window changes. To deliberately re-derive (e.g. after adding an extra brand for the current month), **delete that month's CSV and rerun**. Replay warns loudly (`unfrozen_candidates`) when current data would match rows that have no frozen decision.
- **Maintenance:** monthly, skim the audit CSV; obvious real brands that stayed generic → add to `GENERIC_RECOVERY_EXTRA_BRANDS` in `full_report_month.py`, delete the current month's CSV, rerun. Never add innova/blcktec.
- **Always run this via `pnpm prelaunch:code-reader`** — a bare `full_report_month.py` invocation defaults to `amazon_obd2/` instead of the carryover dir and would freeze a smaller decision set (replay will warn, but the pipeline should write the CSV first).

### If the pipeline pauses

- **Exit 2 — missing ASINs** (`script/runs/YYYYMM/missing.xlsx` written): upload the generated batch files `script/runs/YYYYMM/helium10_batches/asins_batch_*.txt` (≤200 ASINs each) to Helium10, save the returned exports into `Amazon_Raw_Data/backup_data/YYYYMM/`, build `missing-good.csv` if needed, then **rerun the same command**. Only if Helium10 truly has no data: rerun with `--missing-mode carryover_zero` (carries last month's rows forward with 0 current-month units/revenue).
- **Exit 3 — unknown Types** (`script/runs/YYYYMM/extra.xlsx`): auto-categorization runs first (confidence ≥0.90 auto-appends to `amazon_scanner_type.xlsx`, snapshot saved as `amazon_scanner_type.before_auto.xlsx`); review `extra_review_required.xlsx`, add remaining ASIN→Type rows to `amazon_scanner_type.xlsx`, rerun. With `--allow-extra` (default) the pipeline continues with a warning after one auto pass.

## 3. Deliverable #1 & #2 — the two formatted reports

Written to `Amazon_Monthly_Competitor_Report copy/YY-MM-reports/`, date-tagged with the run date:

1. `YY-MM-DD Amazon Competitor Analysis <MonthName>.xlsx` — category/brand Analysis workbook
2. `YY-MM-DDAmazon Competitor Report <MonthName> Innova Adjusted.xlsx` — brand-level report (note: no space after the date tag, per the code)

Formatting is **rule-driven** (logos auto-inserted from `script/brand_header_assets/`, label-driven fills, banding, link fonts, merged rank titles, number formats) and validated at build time — the build fails loudly if any invariant breaks. New brand next month → drop `<tabname>.png` into `script/brand_header_assets/report/` (a warning, not a failure, if missing).

## 4. Local dashboard update (Docker Postgres + chatbot)

**What goes into Docker:** only Postgres runs in Docker. The monthly ingest (stage 4 above) writes one new snapshot for `category_id = code_reader_scanner`, month `YYYYMM`, into these tables: `ingestion_runs`, `category_snapshots`, `snapshot_rows`, `snapshot_products`, `snapshot_brand_totals`, `snapshot_price_tiers`, `snapshot_rolling_12`, `snapshot_type_breakdowns`, `snapshot_category_brand_mix`, `snapshot_feature_premiums`, plus the source xlsx files as blobs in `source_artifacts`. **No full reload each month — incremental only.**

If you ever need to re-run just the ingest (e.g. after fixing data) without the whole pipeline:

```bash
pnpm db:ingest:code-reader -- --month YYYYMM \
  --report "../Amazon_Monthly_Competitor_Report copy/script output reports/Amazon Competitor Report.xlsx" \
  --summary "../Amazon_Monthly_Competitor_Report copy/script output reports/summary.xlsx" \
  --structured-json "../Amazon_Monthly_Competitor_Report copy/script output reports/dashboard_snapshot_rows.json" \
  --source-mode raw_unformatted
```

**Chatbot:** the dashboard chatbot (`app/api/chat`) is deterministic-first and reads the **same Postgres snapshot data** as the dashboard (`loadDashboardData()`, 15s in-process cache). Once the monthly ingest + revalidation completes, the chatbot answers with current-month data automatically — no separate refresh step. `OPENAI_API_KEY` / `OPENAI_MODEL` are optional (LLM only rephrases low-confidence answers; the bot works without them). The separate "Consult-me" research feature (Valyu API) is not part of the monthly flow.

**Local verification:** `pnpm -C product_dashboard dev` → open the dashboard, confirm the new month appears; ask the chatbot a question about the new month.

## 5. Production sync & deploy (Neon + Vercel)

Production reads a **Neon Postgres** (PG 17), not your local Docker DB, so the data must be ingested a second time against Neon.

1. **Ingest into Neon:** temporarily point env at Neon (either export `DATABASE_URL` / `DATABASE_URL_UNPOOLED` with the Neon connection strings in your shell, or use a dedicated env file) and run, from `product_dashboard/`:
   ```bash
   pnpm db:migrate                # first time / after schema changes only
   pnpm db:ingest:code-reader -- --month YYYYMM --report ... --summary ... --structured-json ... --source-mode raw_unformatted
   ```
   Then restore your local env. The ingest triggers remote revalidation when `DASHBOARD_REVALIDATE_URL` + `DASHBOARD_REVALIDATE_SECRET` are set.
2. **Commit & push code/data changes** to **`main`**:
   ```bash
   git add <changed files>        # e.g. scripts, amazon_scanner_type.xlsx, YY-MM-reports/, data archives
   git commit -m "Add <Month> YYYY code reader dashboard data"
   git push origin main
   ```
   Vercel's GitHub integration auto-builds and deploys **`main`** to production (project `product-market-research`, Root Directory = `product_dashboard`, configured in the Vercel dashboard — there is no `vercel.json`). Other branches produce Preview deploys with Neon preview DB branches.
3. **Production env vars** (set in Vercel, names only): `DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `DASHBOARD_DATA_SOURCE=postgres`, `DASHBOARD_DEPLOYMENT_MODE` (`code_reader_only` on Vercel), `DASHBOARD_REVALIDATE_SECRET`, `DASHBOARD_REVALIDATE_URL`, plus optional `OPENAI_API_KEY`/`OPENAI_MODEL` for chatbot polish.
4. **Post-deploy checks:**
   ```bash
   pnpm deploy:check-env
   pnpm db:verify:parity          # file vs Postgres parity
   pnpm deploy:smoke -- --base-url https://<production-domain>
   ```

Reference: `product_dashboard/docs/neon-vercel-production.md` and `product_dashboard/docs/monthly-operator-checklists.md`.

## 7. Known pitfalls

1. ~~**Hardcoded dashboard path**~~ (fixed): `script/run_prelaunch_dashboard_pipeline.py` used to point its ingest at a stale worktree copy (`.claude/worktrees/serene-davinci-64d1ec/product_dashboard`); it now resolves the real `product_dashboard` next to the report repo.
2. **Folder month vs export date:** the `raw_data/YYYYMM` folder is the *report* month; the CSVs inside are dated early the *following* month. Don't create the folder from the file dates.
3. **13-month history:** never delete old `amazon_obd2/amazon_obd2_*.xlsx` files — `full_report_month.py` hard-fails without a complete 13-month window.
4. **Templates are last month's finals:** the two formatted reports are built on top of the previous month's files in `YY-MM-reports/`. If you rename or move them, pass `--template-report` / `--template-analysis` explicitly.
5. **BLCKTEC file naming:** `blcktecYYYYMM.xlsx` — no underscore. `innova1p_`/`innova3p_` — with underscore.
6. **New competitor brand appears:** the report gets a new tab automatically (cloned + recolored); add `script/brand_header_assets/report/<tabname>.png` to give it a logo (warning only if absent). Brands to exclude from tabs are listed in `EXCLUDED_BRAND_SHEETS` (report_fill/main.py).
7. **Don't run `db:backfill` monthly** — it's for empty databases only; monthly is incremental ingest.
8. **Non-code categories** have their own commands and data dirs (`product_dashboard/data/non_code_categories/**`); keep those changes in separate commits from the code-reader monthly update when possible.
9. **Raw rolling labels vs the dashboard chart (fixed 2026-09-02):** the RAW report's "Rolling 12 mo" headers are metric-relative (`Monthly Revenue-11…`, `Monthly Sales-11…`), which used to break the dashboard's Brand monthly trend card when a raw report was ingested (revenue/units labels must match index-wise). The ingest parser now normalizes relative labels to real month names using the ingest month (`lib/code-reader-scanner-data.ts`; issues `rolling_relative_labels*` / `rolling_label_sections_misaligned` warn on malformed headers instead of guessing). Convention unchanged: the committed month archive and prod re-ingests use the FORMATTED report (real labels), like every prior month.
